DÉCADA

Recebe o plano alimentar de uma nutricionista em PDF, traduz cada item prescrito em produto real de supermercado, calcula o custo da compra por região e sugere receitas com o que já existe em casa.

O aplicativo não prescreve dieta. Ele operacionaliza uma prescrição que já existe.

Arquitetura

Camadas que não se conhecem

As regras de negócio ficam em app/services/ e não conhecem HTTP. Isso não é promessa de documento: da primeira à oitava etapa o projeto não tinha nenhuma rota, e casamento de produtos, cálculo de preço, despensa e receitas já funcionavam e já tinham teste. A API veio depois, só expondo o que existia.

Telas em React Native. Formata, agrupa e exibe.

Agrupar a lista por corredor do mercado é decisão daqui, não do servidor.

API

Escopo

O que ficou de fora, e por quê

Cada ausência abaixo foi decisão, não esquecimento. Numa banca, isso costuma valer mais do que a lista do que foi usado.

  • fora

    OCR de foto do plano

    Só PDF com texto. Foto de papel exigiria Tesseract ou serviço externo, com resultado difícil de testar de forma determinística. O aplicativo recusa o arquivo com uma mensagem que explica o motivo, em vez de tratá-lo como plano vazio.

  • fora

    Redux, Zustand e afins

    Quase todo estado do aplicativo é estado do servidor. TanStack Query já cuida de cache, revalidação, carregamento e erro. Uma biblioteca de estado global resolveria um problema que o projeto não tem.

  • fora

    AsyncStorage para a sessão

    Guardaria o token em texto puro no disco, e esse token dá acesso a plano alimentar, que é dado sensível de saúde. Usa-se armazenamento cifrado pelo sistema operacional.

  • fora

    Tailwind, NativeWind, styled-components

    Os tokens do sistema de design viraram um arquivo TypeScript tipado. Errar o nome de uma cor é erro de compilação, não uma classe que silenciosamente não existe.

  • fora

    GraphQL

    Um cliente só, telas conhecidas, contratos estáveis. REST resolve, e a documentação sai de graça do FastAPI.

  • fora

    Cache, fila e microsserviços

    A prioridade declarada do projeto é MVP funcional e bem documentado, não escala de produção. Nada aqui tem carga que justifique Redis ou fila de mensagens.

  • fora

    Docker para a aplicação, CI e ambiente publicado

    O Docker sobe apenas o Postgres. O backend roda no ambiente virtual local e o aplicativo pelo Expo. Não há integração contínua nem ambiente publicado — é a lacuna mais visível para quem olha com olhos de produção.

Engenharia

Cinco decisões que sustentam o resto

  1. Preço nunca viaja sozinho

    Todo valor carrega data da coleta, origem e tamanho da amostra. Preço com mais de trinta dias aparece rotulado como estimativa. Região sem coleta devolve ausência de preço, nunca R$ 0,00 — porque zero é uma mentira específica. A regra é testada no cálculo, na API e na tela.

  2. O casamento item–produto nunca é automático

    O sistema ordena candidatos por semelhança; quem confirma é o usuário. Nem durante o import, nem com cem por cento de semelhança. É a diferença entre uma ferramenta e um palpite.

  3. A LGPD virou código

    A função que importa o plano exige a data do consentimento como argumento obrigatório sem valor padrão: não existe caminho no código que grave um plano alimentar sem registrar o aceite. Apagar a conta apaga de verdade, sem exclusão lógica, e só o preço sobrevive anonimizado. Recurso de outra pessoa responde 404, e não 403, porque “existe, mas não é seu” já revelaria que aquela pessoa tem um plano alimentar.

  4. As regras de exclusão estão travadas por teste

    Um arquivo de teste verifica cada ON DELETE declarado no banco. Trocar um CASCADE por SET NULL sem pensar quebra a suíte. A política de dados do projeto mora no schema, e o schema está protegido.

  5. Uma costura que se provou

    A autenticação chegou depois da API. Até lá, as rotas identificavam o usuário por um cabeçalho provisório, isolado numa única função. Trocar aquilo por token assinado mudou essa função e mais nada — nenhuma rota, nenhum teste de rota. Foi decisão deliberada de projeto, e funcionou como previsto.

Limites

O que ainda não existe

Não há nenhum preço real no sistema

A decisão do projeto é que a fonte principal de preço seja o QR Code da nota fiscal eletrônica escaneado pelo usuário — e essa leitura não foi implementada. Hoje todos os preços vêm de um catálogo fictício, marcado como tal no banco e sinalizado na tela. O sistema está completo; os dados não são reais.

  • Leitura de PDF de plano real. O filtro que separa alimento de cabeçalho foi calibrado em planos de uma linha por item. Num plano real, que quebra o item em duas linhas e traz parágrafos de substituição, foram extraídos cinquenta itens com apenas dezessete reconhecidos.
  • Aba Economia. Prevista na navegação, ainda sem tela.
  • Refeições com horário e status. O protótipo mostra a rotina do dia com o que já foi consumido; o modelo de dados ainda trata o plano como lista única de itens.
  • Vincular ao catálogo um item já salvo na despensa. A escolha do produto só acontece no momento de adicionar.

Adiante

Próximas etapas

Em ordem de valor para o produto. Os candidatos técnicos são propostas — nenhum foi decidido. A regra do projeto é discutir decisão de arquitetura antes de escolher sozinho.

  1. Nota fiscal eletrônica por QR Code

    proposto

    É o que transforma o projeto em produto. Sem ela não há preço real, e todo o cálculo de preço, que já está pronto e testado, fica esperando dados.

    Candidatos: expo-camera para a leitura do código; um parser da página da nota que a Secretaria da Fazenda publica; regra de idempotência pela chave de acesso, para o mesmo cupom não entrar duas vezes.

  2. Leitura de planos reais

    proposto

    Três regras cobririam a maior parte dos casos observados: linha iniciada por hífen é continuação da anterior; linha que não começa com maiúscula é continuação de parágrafo; bloco iniciado por “Substituição” é seção, não alimento.

    Candidatos: nenhuma biblioteca nova — é evolução do filtro que já existe, com um conjunto de PDFs reais servindo de teste.

  3. Refeições com horário e registro de consumo

    proposto

    Destrava a tela mais rica do protótipo. Exige um modelo de refeição entre o plano e o item, e um parser que reconheça os cabeçalhos de refeição em vez de descartá-los.

  4. Integração contínua e aplicativo instalável

    proposto

    Hoje os testes rodam só na máquina de quem programa, e o aplicativo só roda pelo Expo em modo de desenvolvimento.

    Candidatos: GitHub Actions executando pytest e jest a cada envio; EAS Build para gerar um arquivo instalável de Android.

  5. Dívidas técnicas já mapeadas

    registrado

    Recusar a subida da aplicação fora de desenvolvimento se a chave que assina os tokens for a padrão ou for curta demais. E acelerar a suíte de testes, hoje em quatro minutos porque quase todo teste recarrega o catálogo inteiro.
